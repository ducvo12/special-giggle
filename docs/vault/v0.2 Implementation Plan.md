## Detailed Pass Specifications

### Pre-v0.2 — "Archon" Identity & Visual Cockpit (Stage 1)

#### 1. The Issue Addressed
The application initially carried generic filler branding ("Granite") and monochrome dark styling. To establish a distinct personality and hacker-cockpit vibe before building deep feature passes, it needs a cohesive identity: celestial authority, a recognizable motif, and tactile terminal cues.

#### 2. Delivered Technical Scope
- **Rebranding Core Strings:** Update the primary application header, window titles, and empty states from "Granite" to "Archon".
- **Celestial Iconography:** Design and embed the custom shooting star SVG icon into the desktop header and empty-chat state.
- **Terminal Prompt Glyph:** Style the composer input line with the prompt glyph (`✦ archon:~$ `) and monospace command hints.
- **Design Tokens:** Formalize all color surfaces, starlight amber accents, precision radii, and typography in `tokens.css`.

#### 3. Educational Concept & Learning Attachment
- **Topic:** *Design Tokens, Semantic Variables, and Preventing Agent Visual Drift.*
- **Why this matters:** When autonomous coding agents write UI code over time, they introduce inconsistent padding, raw hex colors, and mismatched borders unless constrained by strict semantic tokens.
- **What to study:**
  - Study design system token architecture (W3C Design Tokens Community Group specification).
  - Inspect how CSS custom properties isolate theme changes from component implementations.

#### 4. Verification & Acceptance Criteria
- App header prominently renders the shooting star icon and "Archon" title.
- Chat empty state renders the celestial branding.
- Chat composer displays the prompt glyph with starlight amber focus glow.
- `npm run lint` and `npm run build` pass cleanly with 0 errors.

### v0.2 Pass 1 — Retired: Filesystem Chats & Terminal Navigation

Scope revised November 9, 2026:
- **Cancel composer navigation commands:** Do not implement `cd`, `pwd`, `ls`, or `clear`. Long chat titles make name-based command navigation inconvenient; keep existing navigation.
- **Retain SQLite as authoritative storage:** Do not migrate chats to filesystem transcripts or continuously maintain duplicate JSONL/Markdown logs. The additional persistence and synchronization work does not provide enough agentic benefit for this scope.
- **On-demand logs only:** If transcript download/export is added, generate the requested log from saved conversation data when the user requests it. Export format and UI remain future decisions; export is not required before the next pass.
- **Defer remaining ergonomics:** Broader file-type browsing/previews and `Cmd/Ctrl+T` are not prerequisites for the next pass and are not cancelled by the storage/navigation decision. Revisit them separately if needed; preserve existing file viewing.
- **Retire the associated learning exercise:** The file-backed storage and REPL topics no longer justify implementation work in this pass.

**Current priority (November 9, 2026):** Code readability and understanding the existing codebase. Pass 2 is postponed; keep later pass numbers unchanged.

### v0.2 Pass 2 — External IDE Launch & Process Hand-off

**Status (November 9, 2026):** Postponed while the user reviews code readability and learns the existing codebase. Scope is retained for later implementation.

#### 1. The Issue Addressed
Many developer tools make the mistake of embedding a rudimentary text editor inside their own window. This forces developers to sacrifice their configured keybindings (Vim, Emacs), custom themes, language servers (LSP), and installed extensions. Granite should get out of the way and let developers use their favorite IDE.

#### 2. Delivered Technical Scope
- **Platform scope (November 9, 2026):** Implement and verify macOS support in this pass. Defer Windows-specific editor discovery, launch handling, path/URI handling, and verification until release preparation. Shared editor settings and launch requests should remain platform-neutral where straightforward; do not add speculative Windows branches.
- **Configurable External Editor:** Settings option to select preferred editor:
  - Visual Studio Code (`code`)
  - Cursor (`cursor`)
  - Zed (`zed`)
  - JetBrains IDEs (IntelliJ, WebStorm, PyCharm)
  - System default / Terminal `$EDITOR`
- **One-Click Launch:** Clicking a repository header or file path opens the codebase directly in the chosen IDE.
- **Line-Targeted Deep Linking:** Clicking a file link in a chat response opens the exact file and cursor position (`file:line:col`) in the external IDE via URI schemes:
  ```text
  vscode://file/{path}:{line}:{column}
  cursor://file/{path}:{line}:{column}
  zed://file/{path}:{line}:{column}
  ```

#### 3. Educational Concept & Learning Attachment
- **Topic:** *OS Deep Linking, URL Schemes, and Process Detachment.*
- **Why this matters:** Learn how macOS LaunchServices and editor command-line launchers delegate tasks across process boundaries. Windows-specific mechanisms are deferred until release preparation.
- **What to study:**
  - Study Electron's `shell.openExternal` and `child_process.spawn` with `detached: true, stdio: 'ignore'`.
  - Learn how VS Code and Cursor register custom URI handlers (`vscode://`, `cursor://`) to receive external file-opening commands without spawning duplicate application windows.

#### 4. Verification & Acceptance Criteria
- All acceptance checks in this pass run on macOS. Windows support is not claimed until its release-preparation implementation and verification are complete.
- Clicking "Open in IDE" launches the selected editor pointed at the repository root.
- Clicking a file citation with line numbers opens that exact line in the editor.
- Closing Granite does not terminate the launched IDE.
- If the configured editor is not installed, Granite surfaces a helpful fallback prompt without hanging.

### v0.2 Pass 3 — Isolated Git Worktrees & Branch Concurrency

#### 1. The Issue Addressed
In v0.1, when an agent edits repository files and runs tests, it operates directly in the repository directory on disk. If the user is currently writing code in that same repository, the agent and the human collide:
- The human's uncommitted changes get tangled with the agent's changes.
- Running tests can fail because the working tree has half-written human code.
- You cannot easily test two different agent approaches in parallel.

#### 2. Delivered Technical Scope
- **Git Worktree Isolation:** When starting a coding chat, Granite can spawn a dedicated, lightweight Git worktree:
  ```sh
  git worktree add .granite/worktrees/<chat-id> -b granite/<chat-id>
  ```
- **Isolated Execution:** All agent file edits, git commits, terminal runs, and previews execute within that private worktree directory. The developer's main working tree remains completely clean and untouched.
- **Review & Merge Workflow:**
  - Inspect unified diffs between the worktree branch and `main`.
  - Single-click **"Merge into Main"** (or create PR) when satisfied.
  - Safe teardown: `git worktree remove` cleanly prunes the temporary directory.

#### 3. Educational Concept & Learning Attachment
- **Topic:** *Working Tree Isolation & The Agent-Computer Interface (ACI).*
- **Why this matters:** This is the core architectural mechanism used by frontier evaluation harnesses like **SWE-bench** and **SWE-agent** to test agents safely without destroying production code.
- **What to study:**
  - Read: *SWE-agent: Agent-Computer Interfaces Enable Software Engineering Language Models* (Princeton, 2024).
  - Study how `git worktree` shares the underlying `.git` object database across multiple working checkouts with zero disk duplication.

#### 4. Verification & Acceptance Criteria
- Agent runs execute in an isolated worktree path; developer's active branch files remain unmodified during the run.
- Multiple chats can run in parallel on separate worktrees without git index locking errors (`.git/index.lock`).
- User can merge the worktree branch into the primary checkout cleanly.
- Deleting the chat cleans up the worktree directory without leaving orphan git metadata.

### v0.2 Pass 4 — Same-Section Repository Access Grants

#### 1. The Issue Addressed
Modern development frequently involves multi-repository setups (e.g. `backend-api` and `frontend-web` living in sibling projects). In v0.1, a chat inside Project A was strictly forbidden from editing Project B's repository. Developers had to manually copy schemas or switch chats back and forth.

#### 2. Delivered Technical Scope
- **Explicit Cross-Project Grant:** A chat in Project A can request access to edit a sibling Project B within the same Section.
- **Interactive Human Consent:** Granite prompts the user: *"Agent in 'Frontend' requests permission to read/edit 'Backend API'. Allow for this session?"*
- **Strict Section Containment:** Grants can **never** cross Section boundaries. A Closed section can never access a Shared section's repository or vice versa.

#### 3. Educational Concept & Learning Attachment
- **Topic:** *Capability-Based Access Control (CapBAC) vs. Access Control Lists (ACLs).*
- **Why this matters:** Learn how modern security architectures grant ephemeral, scoped capabilities rather than granting permanent superuser/root permissions.
- **What to study:**
  - Study how capability tokens work in distributed operating systems and secure microkernels.
  - Analyze why section boundaries must remain mathematical invariants that cannot be overridden by prompt engineering.

#### 4. Verification & Acceptance Criteria
- Attempting to access another section's repository is blocked at the backend schema level.
- Sibling repository access requires explicit human approval.
- Granted access is revoked when the session ends or user clicks Revoke in Task Permissions.

### v0.2 Pass 5 — Documentation Search & Live Web Retrieval

#### 1. The Issue Addressed
Open-source and local models (e.g. via Ollama or LM Studio) frequently fail when coding with modern frameworks because their training cutoff predates the latest API releases (e.g. Next.js 15 App Router changes, Vite 6, Tailwind v4). Without external documentation, the model hallucinates obsolete syntax.

#### 2. Delivered Technical Scope
- **Bounded Search & Fetch Tools:**
  - `search_docs(query, domain)` — Search official developer documentation.
  - `fetch_doc(url)` — Retrieve and sanitize web documentation into clean Markdown.
- **Domain Whitelisting & Guardrails:** Restrict web lookups to approved documentation domains (e.g. `developer.mozilla.org`, `nextjs.org`, `react.dev`) to prevent prompt-injection attacks from untrusted websites.
- **Context-Efficient Injection:** Convert bulky HTML into compact markdown with headers and code blocks, stripping navigation menus and ads before feeding tokens to the model.

#### 3. Educational Concept & Learning Attachment
- **Topic:** *Tool-Boundary Retrieval-Augmented Generation (RAG).*
- **Why this matters:** Understand why injecting live documentation via structured tool calls is superior to dumping massive static context into system prompts.
- **What to study:**
  - Study HTML-to-Markdown sanitization (Turndown / Readability algorithms).
  - Analyze prompt-injection vectors where malicious websites attempt to hijack agent tool calls.

#### 4. Verification & Acceptance Criteria
- Model can invoke `search_docs` and receive relevant excerpts with clickable source URLs.
- Raw HTML is cleanly stripped of scripts, styles, and boilerplate before entering context.
- Requests to non-whitelisted domains require explicit user confirmation.

### v0.2 Pass 6 — Managed Browser Verification & Frontend Diagnostics

#### 1. The Issue Addressed
When an agent builds a web application, it currently relies on compiler/build errors. If the build succeeds but the app crashes in the browser (e.g. a React `TypeError: Cannot read properties of undefined` in a `useEffect`, or a CSS layout overflow), the agent declares victory while the app is actually broken.

#### 2. Delivered Technical Scope
- **Headless Dev Diagnostic Runner:** When a managed dev preview server is running, the agent can launch a lightweight headless browser instance (via Chrome DevTools Protocol / Playwright).
- **Automated Client Health Check:**
  - Navigates to the local preview URL (`http://localhost:<port>`).
  - Captures browser console errors (`console.error`, unhandled exceptions).
  - Captures network failures (failed API fetches returning 404/500).
  - Takes a viewport screenshot for visual inspection.
- **Feedback Loop:** Returns detected console backtraces directly to the model as diagnostic observations so it can fix the runtime bug before completing the turn.

#### 3. Educational Concept & Learning Attachment
- **Topic:** *Closed-Loop Verbal Reinforcement (The Reflexion Architecture).*
- **Why this matters:** Discover how models learn to debug complex programs by observing the environment's execution feedback rather than relying on one-shot generation.
- **What to study:**
  - Read: *Reflexion: Language Agents with Verbal Reinforcement Learning* (Shinn et al., 2023).
  - Study how Chrome DevTools Protocol (CDP) streams console events and network activity over WebSockets.

#### 4. Verification & Acceptance Criteria
- Introducing a deliberate frontend runtime crash (e.g. `undefined.map()`) is captured by the diagnostic tool.
- Console error stack trace is returned to the model context.
- Model uses the backtrace to identify the bug and apply a corrective patch.

### v0.2 Pass 7 — Modular Tiling Window Manager

#### 1. The Issue Addressed
Granite's 3-column layout (Explorer, Chat, Diff/Editor) is statically locked. Developers working across multiple monitors or with complex multi-file tasks cannot pop out panels, split chats side-by-side, or rearrange their workstation workspace like in Linux tiling window managers (i3/bspwm) or VS Code.

#### 2. Delivered Technical Scope
- **Tiling Pane Architecture:** Refactor the top-level viewport into modular tile containers (`<Tile>`, `<SplitPane>`).
- **Draggable & Dockable Layout:** Drag pane header tabs to dock sections horizontally, vertically, or into tabbed groupings with ghost drop indicator previews.
- **Layout State Persistence:** Persist user pane arrangements to disk/local storage so customized workstation setups survive application restarts.

#### 3. Educational Concept & Learning Attachment
- **Topic:** *Hierarchical Split-Pane Trees, Binary Space Partitioning, and Viewport State Persistence.*
- **Why this matters:** Study how modern IDEs and window managers represent complex multi-pane layouts as binary space partitioning (BSP) trees or flex-box layout graphs.
- **What to study:**
  - Study BSP tree layout algorithms (e.g., how i3, tmux, or VS Code grid layouts serialize to JSON).
  - Analyze pointer event handling and ghost drop-zones during drag-and-drop operations.

#### 4. Verification & Acceptance Criteria
- User can drag any pane (Explorer, Chat, Diff) to split the viewport horizontally or vertically.
- Closing and reopening the app restores the exact tile arrangement.
- Keyboard navigation focus hops cleanly between active tiles.
