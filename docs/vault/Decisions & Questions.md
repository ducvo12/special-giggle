## Proposal history

**P-001 — Superseded:** temporary chats inside projects are prohibited by D-026. Section-level temporary chats read project context without joining the project.

**P-002 — Accepted in D-028:** one undeletable, Shared General section contains both permanent and temporary chats, and no projects. A per-chat temporary marker/retention setting replaces the separate Temporary section.

**P-003 — Accepted in D-042:** when a single-file edit fails validation because the file changed, reject it without mutation, return a tool error to the model, and allow a fresh read plus one corrected edit attempt. On another failure, stop automatic editing for that branch and report partial work. Earlier successful edits are not automatically undone by this rejection; Stop rollback and unknown/partial effects have separate policies. See [[Run Lifecycle Design]] and [[Run Lifecycle - Repository Edits.canvas]].

**P-004 — Deferred by D-067 after initial acceptance in D-043:** the earlier tracked-file rollback proposal is preserved in [[Deferred File Restoration]] and [[Deferred File Restoration.canvas]]. Version one cancels/settles work and keeps completed edits on Stop, crash and chat deletion. It does not require durable before-file snapshots solely for undo. Revision/conflict checks and genuine outcome reconciliation remain required.

**P-005 — Accepted in D-045, updated by D-064/D-067:** steering retains task/history, ordered new messages and actual outcomes in the same run. Hold unstarted actions and cancel obsolete generation or wait for a safe boundary. Refresh permissions for subsequent requests/actions; preserve completed edits. Stop takes precedence and keeps edits, with automatic restoration deferred. See [[Run Lifecycle Design]].

**P-006 — Accepted in D-046, updated by D-067:** retry a transient model-request failure once before response data, otherwise keep partial output/completed edits and offer Continue as a new run. Never replay tools or silently switch providers. Stop of either run keeps completed edits; automatic undo is deferred. Genuine unknown outcomes retain their reconciliation path.

**P-007 — Accepted in D-047:** for a permitted identity edit, show the exact diff, pause the run for a decision, then apply the approved change once or return denial with no file change. Approval is scoped to the action/revision/run; ordinary steering withdraws it, and Stop/deletion/expiry invalidates it. No automatic approval or new per-edit code approval. New personality applies from the next run. See [[Run Lifecycle Design]] and [[Run Lifecycle - Approvals.canvas]].

**P-008 — Revised by D-048/D-054; cleanup details remain proposed:** hold a full hour during active or queued work, and refresh it on agent responses and qualifying actions. Count down from a fresh hour when no work remains or when waiting solely for user approval/input. Store one expiry value plus ordinary run/queue state rather than an activity log. Expiry during active/queued work is superseded. Proposed cleanup only marks eligible due idle/approval-only chats unavailable, cancels residual work/approvals and prevents late callbacks from recreating data. Passive UI activity classification and held-timer crash/queue recovery remain open; D-049 settles permanent-chat deletion. See [[Run Lifecycle Design]] and [[Run Lifecycle - Temporary Expiry.canvas]].

**P-009 — Accepted in D-049, revised by D-067:** active-chat deletion cancels/settles the run, retains completed repository edits and then removes chat-owned data. No automatic rollback is required. Do not delete the codebase/project when deleting a chat. Retain necessary records for genuinely uncertain actions; other chats/fact support follow D-029. See [[Run Lifecycle - Chat Deletion.canvas]].

**P-010 — Accepted in D-050:** keep permitted reads, ordinary project edits, bounded Git inspection and confined/tracked local checks automatic. Require explicit authorization for Git mutations, dependency installation/local-command network access and remote actions; an already-clear user request can supply that authorization without another prompt. All execution paths retain membership/scope checks, and the tracked-file undo promise does not imply reversal of Git history, downloads or external effects. Detailed skill/MCP capability grants and instruction precedence were subsequently accepted in D-051. See [[Tool Permissions]].

**P-011 — Accepted in D-051:** let the agent automatically load relevant enabled skills while the user manages their installation/content. Reuse unchanged authorized MCP connections, apply the ordinary operation/resource permissions to their tools, and defer unrestricted local MCP paths that cannot honor scope/undo rules. Enforce Granite's limits, follow the user's current task/steering over procedural/personality defaults, and treat retrieved content as reference rather than fresh authorization. See [[Skills & MCP Policy]].

**P-012 — Accepted in D-065:** support installation of an identified existing skill package at the user’s request, under `agent/tools/skills/<skill-name>/`, retaining the package resources. Downloading/importing instructions does not execute scripts, install dependencies or enable MCP capabilities. No redundant confirmation for an already-clear installation request; no autonomous authoring or configuration expansion. See [[Skills & MCP Policy]].

**P-013 — Accepted with amendments in D-052/D-053/D-054:** allow independent chats to run concurrently, one active run per chat, whole-run repository ownership for repository-project chats, fair queues, sequential tools, released model capacity during tools/approval and guarded memory updates. The user rejected optional whole-run budgets for the first iteration and replaced queued-temporary countdown with a full-hour hold. Queue displays include the reason and live position; respect host/model concurrency limits. The superseded budget/queued-expiry branches are removed. See [[Concurrency & Limits]] and [[Run Lifecycle - Queues & Concurrency.canvas]].

**P-014 — Accepted in D-056:** preserve pending queued messages across unexpected closure but leave execution stopped until the user explicitly runs them again. Revalidate/requeue as a new run with fresh positions after required recovery. Previously held temporary timers receive a fresh idle hour after recovery; real existing idle deadlines continue offline and already-expired chats are not revived. Invalidate old approvals and make recovered transitions durable so another restart cannot recreate jobs or repeatedly reset expiry. See [[Restarted Queues & Timers]].

**P-015 — Accepted in D-057, revised by D-067:** handle malformed replies and known no-execution corrections, verify uncertain effects before any repeat and retain necessary outcome records while unresolved. Stop/crash keep completed edits. Automatic restoration, full undo snapshots and an old-run Undo interface are deferred. See [[Model & Tool Failures]].

**P-016 — Accepted in D-066:** adopt the Codex-style compact directly available core plus discovery of optional integrations. Use a portable scoped `lookup_tools` path where native provider discovery is unavailable; exact function names and provider internals are not fixed. Filter by current permissions, expose full selected schemas and validate execution separately. Advanced routing/model tuning remain optimization; no whole-run budgets. See [[Tool Selection & Context]] and [[Tool Lookup.canvas]].

**P-017 — Accepted in D-058:** hide repository-mutation tools outside permanent chats in their owning repository project, including from lookup results, while retaining permitted repository reads and separately scoped memory/note updates. Provide compact native context listing/search/reading over eligible saved content, with access filtering before matching, bounded source-linked results and checked detailed reads. Start with indexed text/database lookup and incremental existing summaries. The underlying access rules remain D-019/D-020/D-038/D-039; exact tool names and schemas remain engineering choices. P-016’s broader optional-tool lookup policy is subsequently accepted in D-066. See [[Repository & Context Tools]] and [[Context Retrieval.canvas]].
